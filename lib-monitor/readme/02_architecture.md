# Архитектура и принципы разработки

Библиотека `lib-monitor` построена на принципах модульности, объектно-ориентированного программирования и четкого разделения ответственности (Separation of Concerns).

## 1. Основные компоненты

Архитектура разделена на три логических уровня:

### Уровень объектов (Monitors)
Реализуют логику конкретных экземпляров. Каждый объект инкапсулирует свое состояние, таймеры и callback-функции Astra.
*   `BaseMonitor`: Абстрактный базовый класс, предоставляющий общие методы для управления жизненным циклом, конфигурацией и событиями.
*   `TunerMonitor`: Класс для работы с DVB-адаптерами. Управляет объектами `dvb_tune` и анализирует их статус.
*   `ChannelMonitor`: Класс для мониторинга медиа-потоков. Взаимодействует с модулем `analyze` и отслеживает метрики MPEG-TS.
*   `ResourceMonitor`: Специализированный класс для сбора системных метрик (CPU, RAM, IO).

### Уровень данных (Repositories)
Специализированные модули для регистрации, поиска и централизованного управления жизненным циклом объектов.
*   `BaseRepository`: Базовый класс для всех хранилищ. Обеспечивает потокобезопасный (в контексте Lua-кооперативности) доступ к объектам.
*   `DvbRepository`: Хранилище активных DVB-мониторов.
*   `ChannelRepository`: Хранилище мониторов каналов.

### Уровень управления (Adapters & API)
Высокоуровневые модули, предоставляющие упрощенный интерфейс для внешнего мира.
*   `adapter.lua`: Фасад для работы с тюнерами. Скрывает сложность создания мониторов и взаимодействия с репозиторием.
*   `channel.lua`: Фасад для управления каналами и их мониторингом.
*   `ModuleManager`: Центральный узел системы, отвечающий за загрузку модулей, разрешение зависимостей и управление их жизненным циклом.

## 2. Жизненный цикл монитора

1.  **Инициализация (`new`)**: Создание объекта. На этом этапе происходит валидация конфигурации через `MonitorConfig`. Если параметры некорректны, конструктор возвращает `nil`.
2.  **Запуск (`start`)**: Активация мониторинга. Объект создает необходимые ресурсы Astra (таймеры, входы, анализаторы).
3.  **Работа**: Монитор получает данные от Astra через callback-функции, обновляет внутреннее состояние и генерирует события через `EventDispatcher`.
4.  **Обновление (`update`)**: Динамическое изменение параметров (например, порогов чувствительности) без остановки мониторинга.
5.  **Уничтожение (`destroy`)**: Критически важный этап. Монитор обязан:
    *   Остановить все таймеры (`timer:close()`).
    *   Обнулить callback-функции в структурах Astra.
    *   Закрыть модули (`dvb_tune:close()`, `analyze:close()`).
    *   Освободить таблицы в пул (`TablePool`).

## 3. Принципы разработки

*   **Single Responsibility**: Каждый модуль решает одну задачу. Например, `Logger` только пишет логи, а `FilterEngine` только фильтрует события.
*   **Zero-Allocation Path**: В "горячих" участках кода (обработка событий, сбор метрик) минимизировано создание новых таблиц. Используется `TablePool` для переиспользования объектов.
*   **Fail-Safe**: Любая ошибка в callback-функции или обработчике события оборачивается в `pcall`, чтобы предотвратить крах основного процесса Astra.
*   **Lazy Evaluation**: Тяжелые операции (например, `json.encode`) выполняются только тогда, когда данные действительно затребованы клиентом, и кэшируются до следующего изменения состояния.
